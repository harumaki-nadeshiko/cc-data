This package delivers the workload source and fixed scenario contract. The CC
reference build runs it on exactly two nodes and one socket per node. Scenario
IDs use the same source, seed (`131`), validation schema, primary-thread rule,
and barrier algorithm:

| ID | Scenario |
|---:|---|
| 210 | HA01 local reuse |
| 211 | HA02 remote read |
| 212 | HA03 ownership handoff |
| 213 | HA04 shared read then writer |

The catalog additionally defines 2N1S adapted contracts for TC123, TC130,
TC132, TC135, TC138, and TC139. Their current source files remain fixed 3N1S
workloads, so those entries are specifications, not directly runnable 2N1S
binaries. Do not present them as implemented until a dedicated portable source
and verifier exist.

Run CC profiles with identical inputs:

```bash
EP_PERF_PROFILE=naive bash tests/e2e/run_multi.sh --2n1s 210
EP_PERF_PROFILE=optimized bash tests/e2e/run_multi.sh --2n1s 210
```

Each node emits JSONL `manifest` and `validation` records. The verifier accepts
only a run with successful validation from both nodes.

HA10 adds a portable 512-entry capacity-pressure performance scenario. Node0
streams 640 pressure lines in eight batches while Node1 performs a skewed 90/10
catalog lookup/update mix. It emits eight `catalog_batch` JSONL samples plus a
128-operation `catalog_useful_throughput` sample. The same records can be
generated by an HA target adapter without CC protocol instrumentation.

HA11 and HA12 each exercise exactly 768 unique lines against the 512-entry
ResidentDir: 64 hot lines plus 704 pressure lines, for a capacity ratio of
1.500000. HA11 measures clean/shared admission and first revisit. HA12 measures
dirty-owner admission, first revisit, and ownership handoff. Formal HA01-HA10
matrix runs prepend an independent 768-line capacity precondition so every HA
scenario is executed after the same exact-150% pressure point.

Guest-visible `CNTVCT` samples are emitted for measured phases. Summarize a
completed CC run without using protocol timing as a cross-platform substitute:

```bash
python3 scripts/summarize_2n1s_guest.py \
  --input build/runs/<run>/tc215/m5out/node0/simout_n0 \
          build/runs/<run>/tc215/m5out/node1/simout_n1 \
  --output results/ha05_cc_guest.jsonl
```

## FPGA Target Adaptation

The customer receives the workload source, not an FPGA-specific binary or an
adapter request. To compile on the target, replace the CC-only primitives used
by `e2e_ha_2n1s_core.c` with the target SDK equivalents:

| CC reference primitive | Target-side replacement |
|---|---|
| `dsm_load(home, offset)` / `dsm_store(home, offset, value)` | Load/store to the allocated HA-visible shared range. |
| `sync_wait(0x3)` | Two-participant barrier supplied by the target runtime. |
| `printf` JSONL records | Target console, UART, file, or result transport. |
| `node` / `cpu` command arguments | Target runtime node/thread identity. |

The operation sequence, offsets, values, seed, barrier positions, and JSONL
validation schema must remain unchanged. No proprietary placement, affinity,
timer, cache-control, or FPGA SDK details need to be shared with this project.

The current `e2e_ha_2n1s_core.c` still includes CC reference headers. It is not
a drop-in freestanding binary source. Follow the bare-metal delivery guide to
provide compatible headers or, preferably, extract the scenario body behind a
small `ha_platform_*` adapter.

## CC Diagnostic Results

For CC runs, `scripts/summarize_2n1s_protocol.py` emits JSONL samples and a
summary from completed `EP-PERF kind=outer` records. Its manifest explicitly
marks the result as `cc_outer_protocol`, `guest_visible=false`, and
`cross_platform_comparable=false`. It is useful for CC path diagnosis only;
it is not an FPGA or HA latency claim.

For a completed matrix, collect per-scenario CC protocol diagnostics with:

```bash
python3 scripts/analyze_2n1s_cc.py \
  --log-dir logs/<run> --profile optimized \
  --output /tmp/ha_cc_optimized_protocol.jsonl
```

The output remains `guest_visible=false` and
`cross_platform_comparable=false`.
