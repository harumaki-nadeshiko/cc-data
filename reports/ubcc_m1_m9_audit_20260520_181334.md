# UBCC M1-M9 审核报告

- 时间戳: `20260520_181334`
- 审核对象: `docs/ubcc_agent_execution_guide.md` 中 M1-M9
- 审核方式: 静态代码审查 + 测试资产审查 + 轻量运行验证
- 结论摘要: 当前仓库只有 `M1` 可视为基本完成；`M2` 仅完成了部分配置层脚手架；`M3-M9` 大多停留在 standalone skeleton / compile-only 阶段，没有真正接入 gem5 Ruby CHI 主路径，也没有达到文档要求的端到端验收。

## 总体结论

| 阶段 | 结论 | 判断 |
| --- | --- | --- |
| M1 | 基本完成 | 已接入真实 `--chi-config` 路径，cluster-shared L2 结构存在，但运行证据偏弱 |
| M2 | 部分完成 | 做了多 node config，但没有真正实现严格 domain isolation，也没有 ordinary CHI checker |
| M3 | 未完成 | EP 控制器只是定义和最小收发 skeleton，没有接入系统拓扑 |
| M4 | 未完成 | sentinel 只存在于 EP 私有 map，没有接入 HN-F directory，也没有 synthetic MachineID 语义 |
| M5 | 未完成 | EP-SNF 直接返回 fake data，没有向 home UBCC 请求 data/grant |
| M6 | 未完成 | UBCC directory 只是 standalone C++ 类；EP-RNF 不会执行 local coherent access |
| M7 | 未完成 | 只有 writeback/evict 枚举级处理，没有 owner recall/transfer/epoch 防护闭环 |
| M8 | 未完成 | 只有 `GrantS` 枚举/分支，没有 HN-F->EP-SNF sideband，也没有 requester-side sharer registration |
| M9 | 部分完成 | metadata map 方向符合要求，但 multi-gem5 ABI/时序模型文档与实现均缺失 |

## 关键问题

1. `M3-M9` 的核心问题不是“缺少优化”，而是根本没有接入真实 Ruby/CHI/HN-F 数据通路。
2. 多个“测试”本质上只是对象实例化或打印字符串，不能证明阶段目标已完成。
3. `M2` 的验证用例让非目标 node 基本空跑，无法有效暴露跨 node ordinary CHI 路由错误。
4. `M4-M8` 文档要求的大部分行为都需要修改 HN-F / CHI protocol 主逻辑，但当前仓库几乎没有对应集成代码。

## 运行验证说明

- 仓库内存在 `gem5/build/ARM/gem5.opt`，但本机直接运行失败，缺少共享库 `libhdf5_serial.so.103`。
- 因此本次无法在当前宿主环境复现现有 gem5 运行脚本，只能基于代码与测试内容判断完成度。
- 这不影响主要结论，因为当前大量缺口属于“代码路径根本不存在”，不是“运行时才会暴露的细节错误”。

## 分阶段审核

### M1: Single Node Clustered CHI

**结论:** 基本完成，但验收证据不足。

**已完成证据**

- `gem5/configs/ruby/CHI.py:85-103` 已支持通过 `--chi-config` 加载自定义 CHI 配置模块，这条路径是真实 gem5 CHI 创建路径。
- `gem5/configs/ruby/CHI_single_node_config.py:37-158` 实现了 `ClusterCHI_RNF`。
- `gem5/configs/ruby/CHI_single_node_config.py:96-114` 为每个 cluster 创建 shared L2，并将 L1 downstream 指向 shared L2。
- `gem5/configs/ruby/CHI_single_node_config.py:124-158` 按 `cores_per_cluster=2` 分组 CPU，符合文档中“每 cluster 2 个 core + 1 个 shared L2”的目标。

**不足与风险**

- 我没有找到 repo 内的 gem5 运行脚本、日志或统计输出，来证明文档要求的 4-core single-node SE smoke 确实跑通过。
- `tests/ubcc/smoke_test.c:1-44` 只是 workload 源文件，不是验收记录。
- 文档要求 Ruby debug 中可见 `L1 -> shared L2 -> HN-F -> SN-F` 路径，但仓库内没有对应日志证据。

**修改方案**

1. 增加一个可直接运行的 M1 脚本，固定 `--ruby --ruby-protocol=CHI --chi-config=... --num-cpus=4 --num-l3caches=1 --num-dirs=1`。
2. 将 `tests/ubcc/smoke_test.c` 的构建、运行、统计检查脚本化。
3. 将 Ruby debug 关键路径输出和 stats 摘要作为 M1 验收产物落盘到 `reports/` 或 `artifacts/`。

**需要补充的 Testcase**

1. 单核 smoke: 仅启动 1 个 core，确认 `--chi-config` 生效且 workload 正常退出。
2. 同 cluster 双核共享: `cpu0/cpu1` 读写同一 cache line，验证共享 L2 参与转发/命中。
3. 跨 cluster 共享: `cpu0` 写、`cpu2` 读同一 line，验证路径经过 HN-F/L3。
4. 容量压力: 工作集大于 L1/L2，小于 L3，验证出现 `L1 -> shared L2 -> HN-F`。
5. DRAM 回源: 工作集大于 L3，验证 `SN-F/DRAM` 被访问。
6. 参数反例: `num_cpus` 非 `cores_per_cluster` 整数倍时必须 `fatal`。
7. debug 路径检查: 自动 grep Ruby debug，要求至少出现 `L1`、shared `L2`、`HNF`、`SNF` 相关 trace。

### M2: Logical Domain Isolation

**结论:** 仅部分完成，未达到文档验收。

**已完成证据**

- `gem5/configs/ruby/CHI_multi_node_config.py:35-127` 实现了按 node 分组的 `MultiNodeCHI_RNF`，每 node 固定 2 个 CPU。
- `gem5/configs/ruby/CHI_multi_node_config.py:130-178` 实现了 per-node `MultiNodeCHI_HNF`，并通过 contiguous partition 划分地址范围。
- `gem5/configs/ruby/CHI_multi_node_config.py:181-196` 增加了 per-node `MultiNodeCHI_SNF`。

**未完成/错误点**

- 文档要求 RN-F downstream 只指向同 node HN-F，但 `gem5/configs/ruby/CHI.py:221-229` 仍然把所有 `hnf_dests` 发给每个 RN-F；`CHI_multi_node_config.py:100-108` 只有在 `_strict_downstream=True` 时才会过滤，默认并未启用。
- 文档要求 HN-F downstream 只指向同 node SN-F 或同 node EP-SNF placeholder，但 `gem5/configs/ruby/CHI.py:228-229` 仍对所有 HN-F 统一下发 `mem_dests`。
- 文档要求 ordinary CHI 跨 node checker，但仓库中没有对应 checker/assert 集成代码。
- `tests/ubcc/m2_isolation.c:26-29` 让非 Node0 的核直接退出，这种 workload 无法证明“相同 DSM global PA 的不同 node 访问不会被错误路由”。

**为什么这意味着 M2 没完成**

- 当前隔离主要依赖“地址切片”而不是“拓扑/目的地强隔离”，这与文档要求的 logical island 不是一回事。
- 即便 contiguous partition 在部分 workload 下看起来工作正常，也不能证明 ordinary CHI message 不会跨 node 漏发。

**修改方案**

1. 在 config 层默认强制 strict downstream filtering，不允许依赖 `_strict_downstream` 这种未默认开启的开关。
2. 为 RN-F、HN-F、SN-F、后续 EP 节点建立明确的 per-node destination set。
3. 在 CHI message 发包路径增加跨 node ordinary message 断言或 debug checker。
4. 重写 M2 测试，让多个 node 同时发起 local-normal 与 DSM-view 访问，并检查错误 node 的 HN-F/SNF 统计为零。

**需要补充的 Testcase**

1. Node-local normal PA: Node0 两个 core 访问本地 normal PA，Node1/Node2 不应收到 ordinary CHI message。
2. 双 node 并发 local-normal: Node0 与 Node1 同时访问各自 local-normal PA，互不串扰。
3. 三 node 并发 local-normal: 所有 node 同时压测，checker 必须零告警。
4. DSM 同地址反例: 不同 node 访问同一 DSM global PA，验证不会被 Ruby 路由到错误 HN-F。
5. RN-F downstream 检查: 启动时检查每个 RN-F 的 downstream 目的地仅包含同 node HN-F。
6. HN-F downstream 检查: 检查每个 HN-F 的 downstream 仅包含同 node SN-F/EP-SNF。
7. 跨 node ordinary message 负例: 人工构造错误配置，checker 必须触发断言或告警。
8. 非空闲 node workload: 禁止像当前 `m2_isolation.c` 这样让非目标 node 直接退出，所有 node 至少执行最小有效 payload。

### M3: EP-RNF/EP-SNF Skeleton

**结论:** 只完成了类定义和最小 skeleton，未完成阶段目标。

**已完成证据**

- `gem5/src/mem/ruby/protocol/chi/ep/EPController.py:9-22` 定义了 `EPRNFController` 和 `EPSNFController`。
- `gem5/src/mem/ruby/protocol/chi/ep/EPRNFController.cc:51-91` 可以在收到 snoop 后回固定 response。
- `gem5/src/mem/ruby/protocol/chi/ep/EPSNFController.cc:49-131` 可以对 `ReadNoSnp` 返回固定 fake data。
- `gem5/src/mem/ruby/protocol/chi/ep/SConscript:11-18` 把这些文件编进 CHI build。

**未完成/错误点**

- `gem5/configs/ruby/CHI.py:97-103,181-229` 的真实系统创建流程只实例化 RN-F/MN/HN-F/SN-F，没有实例化任何 EP controller，也没有把 EP 挂到拓扑里。
- 没有代码让 HN-F 把 EP-RNF 当作 snoop destination。
- 没有 outer queue skeleton 与 EP controller 集成。
- `tests/ubcc/run_m3_ep.py:1-21` 只是实例化对象并打印，不能证明 CHI participant 收发路径打通。

**修改方案**

1. 在 CHI 配置层把 EP-RNF/EP-SNF 作为真实 node/controller 插入 RubySystem 和 network topology。
2. 建立 HN-F 到 EP-RNF 的 snoop destination path，建立 HN-F 到 EP-SNF 的 DSM Remote miss path。
3. 用 gem5 workload 驱动一次真实 snoop 和一次真实 `ReadNoSnp` miss，替换当前 print-only 测试。

**需要补充的 Testcase**

1. EP 控制器拓扑接线: 启动后检查 EP-RNF/EP-SNF 已进入 `RubySystem` 和 network nodes。
2. HN-F snoop EP-RNF: 人工插入最小场景，让 HN-F 向 EP-RNF 发出一次 snoop，验证 EP-RNF 实际收包。
3. HN-F miss 到 EP-SNF: DSM Remote miss 触发 `ReadNoSnp` 到 EP-SNF，验证 EP-SNF 实际收包。
4. node_id 追踪: 所有 EP 收发日志都必须带 `node_id`。
5. 非法未接线负例: 如果 EP 未接进 topology，测试必须失败，而不是仅靠实例化通过。

### M4: Sentinel Registration

**结论:** 未完成。

**已完成证据**

- `gem5/src/mem/ruby/protocol/chi/ep/EPRNFController.hh:35-44` 与 `EPRNFController.cc:96-143` 提供了 register/update/remove API。

**未完成/错误点**

- 文档要求 HN-F directory 能登记 EP-RNF sentinel，但当前 sentinel 仅存在于 `EPRNFController` 私有 `SentinelTracker` 中，没有任何 HN-F directory 集成。
- 文档要求 synthetic MachineID，`gem5/src/mem/ruby/protocol/chi/ep/EPRNFController.cc:22-30` 仍然把 EP-RNF 设为普通 `MachineType_Cache`。
- 文档要求 registration 早于 CPU completion，但当前没有 completion hook。
- 文档要求本地 `ReadUnique` 能 snoop EP-RNF，但 `EPRNFController.cc:71-91` 只会固定返回 `Comp_I`，没有 owner/data 语义。
- `tests/ubcc/run_m4_sentinel.py:19-25` 明确写着“通过编译验证”和 “HN-F SLICC integration TODO”，这实际上已经说明 M4 没做完。

**修改方案**

1. 修改 HN-F directory/state machine，使其可以插入、更新、删除 synthetic EP-RNF entry。
2. 引入真正可追踪的 synthetic `MachineID` 或等效 sentinel 身份表示，并保证日志可区分 node/domain。
3. 在 HN-F 的 local permission change 路径中，把 EP-RNF 当作 sharer/owner 参与 snoop。
4. 加入断言: local normal PA 禁止 sentinel；`ExternalOwner` 不得与本地 dirty CPU owner 共存。

**需要补充的 Testcase**

1. 手工登记 `ExternalSharer`: 本地 CPU 对同 line 执行 `ReadUnique`，必须 snoop EP-RNF。
2. 手工登记 `ExternalOwner`: 本地 CPU 对同 line 执行读写，必须先经 EP-RNF/owner path 处理。
3. remove/update sentinel: 对同一 line 执行 insert/update/remove，验证 HN-F directory 状态同步变化。
4. registration 顺序: 检查 sentinel registration 发生在 CPU completion 之前。
5. Local Normal PA 负例: 对 local-normal 地址登记 sentinel 必须被拒绝。
6. dirty owner 冲突负例: 当本地 CPU 已是 dirty owner 时，不允许 `ExternalOwner` 共存。
7. synthetic MachineID 检查: debug 日志中必须能区分 sentinel 身份，而不是普通 cache controller。

### M5: DSM Remote First Miss Bring-up

**结论:** 未完成。

**已完成证据**

- `gem5/src/mem/ruby/protocol/chi/ep/EPSNFController.cc:76-130` 对 `ReadNoSnp` 有最小响应路径。
- `gem5/src/mem/ruby/protocol/chi/ep/UBCCController.cc:88-123` 有 standalone 的 `GlobalReadShared/GlobalReadUnique -> GrantS/GrantM` 分支。

**未完成/错误点**

- 文档要求 EP-SNF 向 home UBCC 请求 data/grant，但 `EPSNFController.cc:104-130` 直接构造 `0xAA` fake data 返回，没有访问 UBCC。
- `UBCCController` 只是 standalone C++ 类，没有被 `EP-SNF` 或 `EP-RNF` 持有和调用。`UBCCController.hh:6-8` 注释说它由 EP-RNF 持有，但 `EPRNFController.hh:52-59` 并没有 UBCC 成员。
- 没有 requester 侧根据 grant 更新 `ExternalSharer` / owner 状态的代码。
- 也没有任何 Node0 读取 Node1 DSM Local 的真实验证。

**修改方案**

1. 把 `UBCCController` 实际挂到 home side controller 上，不再停留在独立工具类。
2. EP-SNF 收到 DSM Remote `ReadNoSnp` 后，必须转 outer request 到 home UBCC，而不是本地 fake data。
3. 请求方根据 `GrantM` / `GrantS` 更新 requester-side EP/HN-F state。
4. 建立最小两节点 DSM Remote read workload，检查 data 来源和 directory 状态。

**需要补充的 Testcase**

1. Node0 读取 Node1 DSM Local: 首次 miss 经 EP-SNF -> UBCC -> home data 返回，验证数据正确。
2. home directory 初始化: first miss 后 home UBCC directory 必须创建正确 entry。
3. 保守 `GrantM` 路径: requester 获得 `GrantM` 后，只记录 global owner，不登记冲突 `ExternalOwner`。
4. `GrantS` 路径: requester 获得 `GrantS` 后，登记 requester EP-RNF `ExternalSharer`。
5. fake data 负例: 修改测试使返回 `0xAA` 无法通过，确保不能靠假数据蒙混过关。
6. 多地址 miss: 连续访问多条 DSM line，验证 directory 不串线。
7. wrong-home 负例: 请求发送到错误 home node 时必须失败或告警。

### M6: UBCC Directory And EP-RNF Local Access

**结论:** 未完成。

**已完成证据**

- `gem5/src/mem/ruby/protocol/chi/ep/UBCCController.hh:47-62` 定义了 per-line `GlobalDirEntry`，包含 `ownerNode`、`sharerMask`、`epoch`。
- `gem5/src/mem/ruby/protocol/chi/ep/UBCCController.cc:158-185` 能创建和更新 directory entry。

**未完成/错误点**

- 文档要求 EP-RNF 支持 local read/downgrade/invalidate/dirty recall，但 `gem5/src/mem/ruby/protocol/chi/ep/EPRNFController.cc:44-68` 对 req/rsp/dat 基本直接忽略。
- 文档要求 HN-F snoop EP-RNF 时，EP-RNF 要等待 UBCC outer transaction 完成后再响应，但当前 `recvSnoopMsg()` 立即 `sendSnoopResp()`。
- 文档要求 remote read local dirty line 必须拿到最新 data，但当前 EP-RNF 永远回复 `Comp_I`，不会回 data。

**修改方案**

1. 给 EP-RNF 增加本地 CHI 操作状态机，用于读本地 line、降级 sharer、失效 owner、召回 dirty data。
2. 让 EP-RNF 的 snoop response 与 UBCC outer transaction 关联，禁止立即固定回复。
3. 为 remote read local dirty line 加入真实数据转发和验证用例。

**需要补充的 Testcase**

1. local read path: EP-RNF 代表外部节点读取本地 clean line，验证能通过本地 CHI domain 获取数据。
2. local invalidate path: 远端获得写权限前，本地 sharer 必须被失效。
3. local downgrade path: 本地 owner 被远端读时必须降级而非直接丢数据。
4. dirty recall path: 本地 dirty line 被 remote read 时必须返回最新数据。
5. snoop-wait 行为: HN-F snoop EP-RNF 后，EP-RNF 必须等待 outer transaction 完成再回包。
6. Node0 read Node1 DSM Local 后，Node1 write 同 line，必须先 invalidate Node0。
7. Node0 write Node1 DSM Local 后，Node2 read 必须看到 Node0 最新写入。

### M7: Writeback, Evict, Owner Transfer

**结论:** 未完成。

**已完成证据**

- `gem5/src/mem/ruby/protocol/chi/ep/UBCCController.cc:126-145` 有 `GlobalWriteback` 与 `GlobalEvict` 的基础分支。

**未完成/错误点**

- 没有 dirty owner recall。
- 没有 M owner transfer。
- `epoch` 只是字段和打印项；`UBCCController.cc:112,163-169` 初始化/传递了 epoch，但没有任何递增、校验或 stale response 防护逻辑。
- 三节点 ping-pong 的关键行为完全没有实现或验证。

**修改方案**

1. 为 directory entry 的 owner/sharer 变更加 epoch 递增。
2. outer response 返回时校验 epoch，丢弃 stale response。
3. 实现 home UBCC 发起 dirty recall 与 owner transfer 的完整路径。
4. 用三节点 ping-pong workload 验证任意时刻仅有一个 global M owner。

**需要补充的 Testcase**

1. dirty writeback: DSM Remote dirty line 回写到 home，验证 home data/state 更新正确。
2. clean evict: clean sharer eviction 后，home sharer mask 正确清除对应 bit。
3. dirty owner recall: remote read 命中 dirty owner，必须收到最新数据并触发 owner downgrade/失效。
4. owner transfer: Node0 持有 M，Node1 写同 line 后，owner 正确转移到 Node1。
5. 三节点 ping-pong: Node0/1/2 轮流写同一 line，任意时刻至多一个 global M owner。
6. stale response 防护: 人工延迟旧 response，验证因 epoch 失配被丢弃。
7. replay/retry: `GlobalRetry` 后重试请求，验证不会破坏 owner/sharer 状态。

### M8: GrantS And Read-Sharing Recovery

**结论:** 未完成。

**已完成证据**

- `gem5/src/mem/ruby/protocol/chi/ep/UBCCController.hh:31-45` 与 `UBCCController.cc:91-108` 中存在 `GlobalReadShared`、`GrantS` 枚举和基本分支。

**未完成/错误点**

- 文档要求 HN-F -> EP-SNF minimal sideband，但 `EPSNFController.hh:39-46` 只有计数器和 node_id，没有 sideband 字段。
- `EPSNFController.cc:49-80` 只根据 `ReadNoSnp` 处理，无法区分 read-only miss 与 unique miss。
- 没有 requester HN-F 在 completion 前登记 requester `ExternalSharer` 的代码。
- 没有后续 local upgrade 触发 global invalidation 的机制。
- 没有“默认启用 GrantS，GrantM 仅为 debug flag”的实现。

**修改方案**

1. 在 HN-F -> EP-SNF 之间传递 `needed_perm=S/M` 或原始 CHI request 类型。
2. Home UBCC 基于权限请求返回 `GrantS` 或 `GrantM`，并维护 sharer mask。
3. Requester HN-F 在 completion 前登记 `ExternalSharer`。
4. 打通 local upgrade -> global invalidate -> sharer 回收路径。
5. 提供可切换的保守 `GrantM` debug flag，但默认测试必须走 `GrantS`。

**需要补充的 Testcase**

1. 双 reader 共享: Node0 和 Node2 同时读 Node1 DSM Local，二者都获得 S。
2. sharer mask 检查: home UBCC directory 中 sharer mask 同时包含 Node0/Node2。
3. local upgrade: Node0 从 S 升级到写权限时，必须使 Node2 invalidate。
4. completion 前登记: 在 requester completion 前检查 `ExternalSharer` 已登记完成。
5. 默认策略检查: 默认测试必须走 `GrantS` 路径，而不是保守 `GrantM`。
6. debug flag 检查: 显式打开保守 `GrantM` flag 时，行为切换正确。
7. 混合流量: 一个 node 读共享，另一个 node 发 unique 请求，验证 invalidation 和权限收敛正确。

### M9: Metadata And Multi-gem5 Preparation

**结论:** 部分完成。

**已完成证据**

- `gem5/src/mem/ruby/protocol/chi/ep/UBCCController.hh:15,116-117` 用 `std::map` 保存 metadata，方向上符合“第一版 metadata 为 C++ map，且不映射给普通 CPU”。
- `UBCCController.hh:79-98` 有 fixed-latency `OuterQueue` 雏形。

**未完成/错误点**

- 没有 outer protocol ABI 抽象层，`OuterMessage` 只是本地 C++ struct，未见序列化/边界定义。
- 没有 multi-gem5 迁移所需字段/时序假设文档。
- 没有 fixed latency / ns-3 / 外部进程 queue 的可切换时间模型接口。
- 当前实现与注释不一致: `UBCCController.hh:6-8` 说 UBCC 由 EP-RNF 持有，但真实 EP-RNF 并未持有它。

**修改方案**

1. 把 `OuterMessage` 提升为明确 ABI，补齐消息字段、序列化格式和版本约束文档。
2. 抽象 transport 层接口，使 fixed-latency queue、ns-3、外部进程 queue 可以替换。
3. 在文档中明确多 gem5 迁移时钟同步、延迟建模、重试与死锁假设。

**需要补充的 Testcase**

1. metadata 不可被 CPU 访问: 普通 CPU 无法通过普通地址空间读取/写入 UBCC metadata。
2. metadata 正确性: 大量 line 插入、更新、删除后，map 中状态一致。
3. fixed-latency queue: 在固定延迟模型下，req/resp ready time 行为正确。
4. transport 抽象一致性: 替换不同 outer transport backend 后，协议语义结果一致。
5. ABI 序列化: `OuterMessage` 编码/解码前后字段完全一致。
6. 版本兼容负例: ABI version 不匹配时，系统必须拒绝或显式报错。
7. 时序假设文档检查: 每个 outer message 字段、顺序、时钟假设都有可执行示例或表格验证。

### 审核判断

这些测试不足以支撑“已完成 M3-M9”的结论，属于明显的弱测试，且存在“面向测试用例编程”的风险: 只要类能编译、对象能创建、打印字符串能执行，测试就会通过，但真实协议路径仍然完全未打通。

## 优先修复顺序

1. 先补完 M2 的严格 domain isolation 和 ordinary CHI checker，否则后续跨 node 语义不可信。
2. 再完成 M3/M4 的真实 EP 接线和 HN-F directory 集成。
3. 然后做 M5/M6 的真正 DSM Remote miss 和 EP-RNF local coherent access。
4. 最后补 M7/M8 的 owner transfer、epoch 防护、GrantS 恢复。
5. M9 应在 correctness 稳定后再做 ABI/多 gem5 抽象，不应假装已完成。

## 最终结论

“已经完成 M1-M9”这一说法不成立。

- 可以认可: `M1` 基本完成，`M2`/`M9` 有部分基础设施。
- 不能认可: `M3-M8` 已完成。当前代码最多只能算是为后续实现准备了一些 skeleton 和工具类。
- 尤其需要指出: `M4-M8` 文档要求的关键语义都依赖与 HN-F / Ruby CHI 主状态机的真实集成，而当前仓库没有对应主路径实现，因此不应宣称阶段完成。
